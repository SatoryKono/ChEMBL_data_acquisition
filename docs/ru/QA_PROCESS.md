# Контроль качества и валидация

Документ описывает проверки, выполняемые конвейерами, форматы отчётов и типовые
приёмы диагностики ошибок.

## Этапы контроля

1. **Входная валидация** — Pandera-схемы (`library/schemas/normalize.py` и
   сущностные схемы) проверяют наличие колонок, допустимые типы и допускаемые
   пропуски до обращения к API.
2. **Валидация обогащённых данных** — после получения данных от внешних
   сервисов итоговые таблицы проверяются схемами, описанными в
   [`OUTPUT.md`](./OUTPUT.md).
3. **Постобработка** — модули `library/postprocessing` приводят порядок колонок,
   сортируют данные по идентификаторам и создают файлы метаданных.
4. **Профили качества** — `library/table_quality.analyze_table_quality` считает
   долю непустых значений, совпадения с шаблонами DOI/ISSN/e-mail/URL и числовую
   статистику. Параметры включения находятся в `system.doc_quality`.
5. **Проверка action type и границ** — обогащение активностей гарантирует, что
   `action_type` соответствует allowlist, а `standard_value` ≥ 0.
6. **Согласование родителей молекул** — обогащение тестовых объектов сверяет
   идентификаторы родителей и булевы флаги со словарями.
7. **Детерминизм** — вспомогательная проверка (`scripts/check_determinism.py` или
   CLI `check-determinism`) сравнивает хэши CSV между запусками.

## Логирование

Используется структурированный логгер `library/common/logging_setup`.

| Поле | Значение |
|------|----------|
| `event` | Название события (`quality_report_failed`, `api_request`, ...). |
| `pipeline` | Имя конвейера (`document`, `target`, ...). |
| `run_id` | UUID запуска. |
| `level` | Уровень (`INFO`, `WARN`, `ERROR`). |
| `details` | Дополнительный контекст (ID, смещения, счётчики повторов). |

Соглашение по уровням:

- **INFO** — штатное выполнение, прогресс, тайминги.
- **WARN** — восстановимые отклонения (отсутствующий DOI, пропущенные колонки в
  профиле, пустой fallback). Предупреждения дублируются в JSON-отчёте качества.
- **ERROR** — нарушение схемы, критическая ошибка API или невозможность записи
  файлов. Конвейер завершается, если не отключён `fatal_on_error`.

## Настройка качества

| Параметр | Где задаётся | Эффект |
|----------|--------------|--------|
| `system.doc_quality.enable` | `config/config.yaml` | Включить/отключить профили качества. |
| `system.doc_quality.sample_rows` | `config/config.yaml` | Ограничить число анализируемых строк. |
| `system.doc_quality.include_columns` / `exclude_columns` | `config/config.yaml` | Управлять списком колонок. |
| `system.doc_quality.fatal_on_error` | `config/config.yaml` | Считать ли ошибки профилирования фатальными. |
| `activity_enrichment.action_type.*` | `config/config.yaml` | Маппинги и allowlist для `action_type`. |
| `activity_bounds.*` | `config/config.yaml` | Правила формирования границ. |
| CLI `--force` / `--skip-existing` | Скрипты конвейеров | Поведение при существующих файлах. |

## Диагностика

1. **Ошибки схемы (`SchemaError`)**
   - Изучите сообщение Pandera: там указаны колонка и проблемное значение.
   - Проверьте разделитель/кодировку (`--sep`, `--encoding`).
   - Убедитесь, что предварительная подготовка не переименовала столбцы.

2. **Сбой профиля качества**
   - Найдите событие `quality_report_failed` в логах. При `fatal_on_error=true`
     конвейер завершится, иначе ошибка будет записана в JSON.
   - Проверьте права на запись и свободное место на диске.

3. **Троттлинг API**
   - Ищите предупреждения `rate_limit_hit` или `retry_attempt`. Настройте лимиты
     через переменные окружения (`CHEMBL_DA_RPS` и др.) или уменьшите `batch_size`.
   - При постоянных 429 увеличьте `backoff_factor`.

4. **Различия между запусками**
   - Используйте `check-determinism --baseline <dir1> --candidate <dir2>`. Игнорируйте
     отличия в метаданных (время), анализируйте именно CSV-хэши.
   - Проверьте, что параметры `--limit` и `--offset` совпадают.

5. **Некорректный `action_type`**
   - Убедитесь, что новые метрики добавлены в `activity_enrichment.action_type.metrics`
     и соответствуют allowlist.
   - Проверьте наличие единиц измерения и `standard_value`; при отсутствии данных
     поле переходит в `unknown`.

## Интеграция в CI

Рекомендуемый пайплайн CI (см. [`development/CI_CD.md`](./development/CI_CD.md))
включает:

- Статический анализ и линтеры.
- `pytest --json-report` с выгрузкой `reports/test_report.json` и `reports/test_summary.md`.
- При необходимости — smoke-запуск конвейеров на примерах + `check-determinism`.
- Smoke-проверки CLI запускают `scripts/get_activity_data.py`,
  `scripts/get_assay_data.py` и `scripts/get_target_data.py` с
  `CHEMBL_DA_OFFLINE=1` на фикстурах `tests/resources/pipeline_inputs`, чтобы
  кешированные ответы оставались совместимыми с парсерами.
- Контроль: доля успешных тестов ≥ 95%.

Рекомендуется загружать QC-отчёты как артефакты. При деградациях создавайте
issue с меткой `data-quality`, приложив:

- Имя конвейера и `run_id`.
- Строки CSV, демонстрирующие проблему (можно обезличить).
- Шаги для воспроизведения (входные файлы, переопределения конфигурации).

## Чек-лист smoke-тестов

Перед крупными мёрджами или релизами выполните smoke-набор и отметьте пункты:

- [ ] `make smoke` — оркестратор на встроенных фикстурах.
- [ ] `make get-activities` — вызывает `python scripts/get_activities.py --limit 25 --dry-run`, проверяя вспомогательный генератор синтетических записей.
- [ ] `check-determinism --baseline <prev> --candidate <curr>` для сравнения последовательных запусков.
- [ ] Отправьте сводку (логи, ссылки на отчёты, вывод команд) в канал `#qa-updates`, чтобы команда QA могла подтвердить результаты.

## Smoke-харнесс CLI

Новый smoke-набор для CLI запускается через `python scripts/run_tests.py -- --maxfail=1 -m smoke`. Обёртка делегирует выполнение `pytest` с включённым плагином `pytest-json-report`, чтобы сохранить сырой протокол и преобразовать его в стандартные отчёты.【F:scripts/run_tests.py†L35-L83】 Установите dev-зависимости (`pip install -e .[dev]`), чтобы гарантированно получить `pytest-json-report` и сопутствующие инструменты.

Успешный прогон формирует артефакты:

- Сырый JSON, структурированный отчёт и Markdown-сводку в `reports/pytest_raw_report.json`, `reports/test_report.json` и `reports/test_summary.md`; вместе с ними пересоздаётся покрытие в `reports/coverage/`.【F:scripts/run_tests.py†L35-L139】【F:scripts/run_tests.py†L708-L834】
- Структурированные логи зеркалируются в `<base>/logs/run_tests_<YYYYMMDD>.log`, где `<base>` определяется через `CHEMBL_DA_BASE_PATH` (если задан) либо используется значение по умолчанию репозитория.【F:library/cli/logging.py†L25-L149】

Харнесс возвращает предсказуемые коды, чтобы CI мог мгновенно отреагировать на деградации:

| Код | Значение |
|-----|----------|
| `0` | Smoke-набор выполнен, пороги по доле успеха и покрытию выдержаны. |
| `1` | Pytest завершился с ошибками или доля успеха/покрытие опустились ниже 95 % / 80 % (`QUALITY_FAILURE_EXIT_CODE`). |
| `11` | Сбой генерации либо валидации структурированных отчётов (`VALIDATION_FAILURE_EXIT_CODE`). |
| `2`, `3`, `4`, `5` | Базовые коды `pytest` передаются без изменений при прерывании, внутренних ошибках, неверных аргументах или отсутствии тестов. |

Обёртка всегда стартует с исходного статуса pytest (`final_exit_code = exit_code`) и лишь при необходимости заменяет его на значения из таблицы, поэтому интеграции продолжают опираться на привычные семантики pytest.【F:scripts/run_tests.py†L56-L59】【F:scripts/run_tests.py†L708-L834】
