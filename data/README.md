# Data directory

This repository ships a small set of reference assets to make the test suite and
usage examples reproducible without a full refresh from upstream ChEMBL
services. The directory is intentionally version-controlled so that developers
have predictable fixtures and can understand how local artefacts are derived.

## Layout and lifecycle

- `input/` – Immutable source fixtures checked into git. These CSV files mirror
  the schemas published by ChEMBL and provide deterministic inputs for tests,
  documentation snippets, and sanity checks. Update them only when the upstream
  schema or curated sample content changes, and mention the provenance in the
  commit message.
- `cache/` – Derived artefacts generated by the ETL jobs (for example, molecule
  cache databases). These files are safe to delete locally; the pipelines will
  recreate them on demand. Commit refreshed caches only when they are required
  for deterministic tests or tutorials, and include a short note in the commit
  that explains the regeneration.
- `logs/` – Checkpoints from sample ETL runs that illustrate the expected
  console output and help troubleshoot regressions in the acquisition scripts.
  These files are updated manually when workflows or logging formats change.

## Where to place runtime output

Runtime output that is purely ephemeral (for example, ad-hoc exports, large
intermediate dumps, or experiment scratch space) should **not** be committed to
`data/`. Instead, place it under an ignored path such as `var/` so that git
stays free of accidental binaries. The `.gitignore` already treats `var/` as a
scratch area, and you can create subdirectories there as needed.

## Working with the directory

- Treat the checked-in files as canonical fixtures. Avoid editing them manually
  unless you also update the associated tests and documentation.
- If you regenerate cached artefacts, clearly describe the command used and why
  the refresh is necessary in the commit message or accompanying docs.
- Keep the directory structure and naming consistent so that automation and
  fellow developers can rely on it without surprises.
